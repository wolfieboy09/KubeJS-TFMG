# Контекст проекта KubeJS TFMG

> Снимок исследования и локальной проверки: 14–15 июля 2026 года. Этот файл — техническая память проекта. При изменении зависимостей, контрактов рецептов или результатов проверки его нужно обновлять в том же pull request.

## Цель порта

Перенести KubeJS TFMG на Minecraft 1.21.1 и NeoForge, сохранив линию Minecraft 1.20.1 отдельно. Первый выпуск должен поддерживать восемь реально существующих типов рецептов TFMG. Экспериментальные конструкторы кабелей и электродов в первый выпуск не входят.

Стратегия доставки: после создания форка ветка `port-1.21.1` публикуется в нём, затем готовится pull request в upstream-ветку `1.21.1`. Если автор не принимает порт, форк остаётся рабочим community-port с сохранением MIT-лицензии и авторства.

Локально создана ветка `port-1.21.1` от `cc761f5`; единственный remote сейчас называется `upstream` и указывает на `wolfieboy09/KubeJS-TFMG`. Форк `Ostoff2/KubeJS-TFMG` не создан: подключённый GitHub API не поддерживает fork, а доступ встроенного браузера к `github.com` запрещён пользовательской политикой. Перед публикацией пользователь должен создать форк или разрешить эту операцию, после чего добавить его как `origin`. Не выполнять push в текущий `upstream`.

## Структура KubeJS TFMG

### Рабочая линия 1.20.1

В `main` Java-код был разделён так:

- `TFMGJS` — точка входа Forge;
- `TFMGJSPlugin` — регистрация KubeJS-схем;
- `recipes/schemas` — общие processing-схемы, отдельные Casting и VAT;
- `recipes/helpers` — обёртки fluid ingredient для старого API KubeJS;
- `cables`, `electrodes`, `KubeJSRegistrate` — заготовки пользовательских реестров.

Рабочая публичная часть — восемь схем рецептов. Вызовы регистрации кабелей и электродов уже были закомментированы в `main`, поэтому они не являются обязательной совместимостью релиза 1.20.1.

Схемы 1.20.1 используют старые классы KubeJS `InputItem`, `OutputItem`, `InputFluid`, `OutputFluid`, массивы и `RecipeConstructor.Factory`. Этот код нельзя просто перекомпилировать на KubeJS 1.21.1.

### Исходная ветка 1.21.1

На SHA `cc761f5` присутствовали только:

```text
├── TFMGJS.java
├── TFMGJSPlugin.java
├── TFMGJSRegistryInfo.java
└── recipes/schemas/
    ├── TFMGRecipeFactory.java
    └── TFMGRecipeSchema.java

src/main/resources/
├── META-INF/mods.toml
├── kubejs.plugins.txt

```

`TFMGJSPlugin` и `TFMGJSRegistryInfo` содержали закомментированную регистрацию, `TFMGRecipeSchema` был пустым, а `TFMGRecipeFactory` не формировал рецепты. То есть ветка собиралась как набросок, но не предоставляла заявленную интеграцию.

В готовом порте основная логика схем находится в `src/main/resources/data/tfmg/kubejs/recipe_schema`. Java-плагин нужен только для общей фабрики/проверки, которую нельзя выразить декларативно.

## Зависимые проекты и их роль

### NeoForge

- Minecraft 1.21.1 требует Java 21.
- Метаданные мода находятся в `META-INF/neoforge.mods.toml`.
- Для обязательных зависимостей применяется `type="required"`; идентификатор загрузчика — `neoforge`, а не `forge`.
- Шаблон метаданных должен быть обработан Gradle до упаковки. В JAR не допускаются необработанные `${...}`.

Документация: <https://docs.neoforged.net/docs/1.21.1/gettingstarted/modfiles/>

### KubeJS 1.21.1

- Рабочая линия исходников — ветка [`2101`](https://github.com/KubeJS-Mods/KubeJS/tree/2101).
- `KubeJSPlugin` теперь является интерфейсом.
- Java-регистрация использует `registerRecipeSchemas(RecipeSchemaRegistry registry)`, а не `RegisterRecipeSchemasEvent` из 1.20.1.
- Предпочтительный способ описания схем — data-driven JSON в реестре `kubejs/recipe_schema`.
- Имена каталогов данных Minecraft 1.21 перешли с множественного числа на единственное: в частности, `recipe`, а не `recipes`.

### KubeJS Create

KubeJS Create становится обязательной зависимостью, потому что он уже описывает компоненты Create: item/fluid ingredients, результаты с шансом, время обработки и нагрев. Базовая схема: [`create:base/processing`](https://github.com/kube-mods/KubeJS-Create/blob/b1f7084a6ef0a7e87a385e5deef17e264377261f/src/main/resources/data/create/kubejs/recipe_schema/base/processing.json); порт наследует `create:base/processing_with_time` через локальную базу `tfmg:base/processing_with_time`.

Локальная база нужна из-за обнаруженной runtime-неоднозначности. В исходной схеме Create fluid-компонент проверяется раньше item-компонента. Обычная строка предмета сначала не проходит fluid-проверку и затем корректно читается как item, но строка `#item_tag` допустима синтаксически и как несуществующий fluid-тег. В результате item-тег бесшумно попадал в fluid-ветку. Порт меняет приоритет только для `ingredients`: сначала `Ingredient`, затем `SizedFluidIngredient`. Явные fluid-объекты (`Fluid.of(...)`, `Fluid.ingredientOf(...)`) всё равно имеют приоритет своего типа. Фактический тип Java-объекта, а не сторона `Either`, используется и при подсчёте границ рецепта.

Это избавляет проект от собственных устаревших fluid wrappers и сохраняет поддержку item components, тегов, количества и вероятностных результатов.

### Create 6

Processing-рецепты Create 6 сериализуются не четырьмя отдельными массивами, как старый KubeJS TFMG, а двумя общими списками:

- `ingredients`: item `Ingredient` или `SizedFluidIngredient`;
- `results`: `ProcessingOutput` для предмета или `FluidStack` для жидкости.

Общие дополнительные поля — `processing_time` и `heat_requirement`. `ProcessingOutput` поддерживает количество, data components и `chance`.

Проверка ограничений существует и в Create, однако KubeJS TFMG должен выдавать более раннюю и понятную ошибку во время загрузки скрипта.

### Create: The Factory Must Grow

Исходники: <https://github.com/DrMango14/Create-The_Factory_Must_Grow/tree/1.21.1>. Стабильная версия 1.2.0 соответствует коммиту [`e55d315`](https://github.com/DrMango14/Create-The_Factory_Must_Grow/commit/e55d31525382ba7106a82ee5db90c7a2571f87ca). На дату снимка default-ветка исходников уже содержала 1.2.3, но последней опубликованной проверяемой версией была 1.2.2; поэтому CI не зависит от неопубликованного состояния исходников.

TFMG регистрирует восемь типов через `TFMGRecipeTypes`. Большинство используют стандартный processing codec Create; `industrial_blasting` и `vat_machine_recipe` добавляют свои поля.

## Контракты рецептов TFMG 1.21.1

| Тип | Item-входы | Fluid-входы | Item-выходы | Fluid-выходы | Дополнительные данные |
|---|---:|---:|---:|---:|---|
| `casting` | 0 | ровно 1 | ровно 1 | 0 | время |
| `coking` | ровно 1 | 0 | ровно 1 | ровно 2 | время |
| `distillation` | 0 | ровно 1 | 0 | 1–6 | время, нагрев |
| `industrial_blasting` | 1–2 | 0 | 0 | 2–3 | время, `hot_air_usage` |
| `polarizing` | ровно 1 | 0 | ровно 1 | 0 | время; поля энергии больше нет |
| `winding` | ровно 2 | 0 | ровно 1 | 0 | время |
| `hot_blast` | 0 | ровно 2 | 0 | ровно 2 | время |
| `vat_machine_recipe` | 0–4 | 0–4 | 0–4 | 0–4 | время, нагрев и VAT-параметры; общие вход и выход не могут быть пустыми |

VAT-поля:

- `min_size`: минимальный размер VAT;
- `heat_level`: числовой уровень нагрева;
- `machines`: упорядоченный список машин/электродов; повторения значимы и не удаляются;
- `allowed_vat_types`: разрешённые типы VAT;
- `pressure`: доступно только начиная с TFMG 1.2.2. На профиле `stable` его использование должно завершать загрузку рецепта понятной ошибкой.

Общая фабрика проверяет `processing_time > 0` и для цепочного метода, и для позиционного аргумента. Унаследованные от Create `.heated()`/`.superheated()` допускаются только для `distillation` и `vat_machine_recipe`; на остальных шести типах вызов отклоняется во время загрузки скрипта, а не позднее в codec. Списки схем допускают временное пустое значение, чтобы итоговые ограничения и понятные сообщения задавала общая фабрика.

`SizedIngredient` от KubeJS Create разворачивается в повторяющиеся item-элементы. Поэтому размер предметного ингредиента учитывается в лимите TFMG: количество 2 допустимо, например, для двух item-входов Industrial Blasting, но превышает лимит Coking в один item-вход. Fluid-количество хранится внутри `SizedFluidIngredient` и не увеличивает число fluid-входов.

Несовместимости, которые нельзя скрывать:

- старое описание KubeJS TFMG разрешало Casting до трёх item-результатов; класс TFMG 1.21.1 допускает один;
- третий аргумент старого Polarizing назывался `energy`, но в TFMG 1.21.1 такого поля нет. Он не должен молча превращаться во время;
- сериализованные поля теперь используют snake_case (`processing_time`, `hot_air_usage`), хотя цепочные методы KubeJS остаются camelCase (`processingTime`, `hotAirUsage`).

## Дефекты исходного каркаса 1.21.1

На SHA `cc761f5` были обнаружены следующие проблемы:

1. Все восемь схем и их регистрация отключены.
2. Curse Maven file `7020555` загружал TFMG 1.1.0b, хотя `gradle.properties` заявлял 1.2.0; стабильный file ID — `7430073`.
3. Указан Registrate для Minecraft 1.20 (`MC1.20-1.3.11`).
4. Версии Flywheel, Ponder, Create и TFMG не образуют проверенную совместимую связку.
5. Задача `generateModMetadata` читает `src/main/templates`, которого нет.
6. Ресурс называется `META-INF/mods.toml`, ссылается на `forge`, использует старое `mandatory=true` и неизвестное `${forge_version_range}`.
7. `pack.mcmeta` содержит формат данных Minecraft 1.20.
8. Пустая mixin-конфигурация заявляет Java 17 при Java toolchain 21.
9. `versions.json` содержит только старые promotions 1.20.1.

## Принятые решения и исключения

- `main` и релизы 1.20.1 не меняются; порт живёт в отдельной ветке.
- Первый релиз охватывает только восемь типов рецептов.
- Кабели, электроды и пользовательские Registrate builders исключены: они не были активны в рабочей версии 1.20.1 и требуют отдельного исследования нового жизненного цикла реестров TFMG.
- Общая механика Create берётся из KubeJS Create вместо копирования классов.
- Сохраняются старые имена методов, если их смысл не изменился. Ложная совместимость для `polarizing.energy` запрещена.
- `pressure` является версионно-зависимой возможностью, а не безусловной частью стабильного API.

Статическая сборка:

```powershell
.\gradlew.bat clean build -PtfmgProfile=stable
.\gradlew.bat clean build -PtfmgProfile=current
.\gradlew.bat clean build -PtfmgProfile=stable '-Pkubejs_version=2101.7.2-build.370'
```

В PowerShell свойство с версией KubeJS заключено в кавычки: без них дефисы и точки могут быть разобраны оболочкой как выражение, а хвост версии попадёт в Gradle как имя задачи.

| Клиент, JEI и реальные машины | не проверены: это интерактивная часть допуска релиза |

Первый server-run выявил три дефекта: item-теги читались как жидкости, пустое начальное значение `machines` блокировало цепочный `.machines(...)`, а проверка типов опиралась на сторону `Either`. Позднее negative-run выявил ещё один важный случай: ошибка цепочного метода возникает уже после создания объекта рецепта. Теперь общий `recipeError` выставляет `removed=true` и `creationError=true`, поэтому KubeJS исключает такой рецепт из финальной карты.

Девять negative-сценариев конструктора/формы увеличивают сырой счётчик KubeJS до `failed=1`. Для `.pressure()` на `stable` и неподдерживаемого `.heated()` KubeJS успевает напечатать `Added 9 recipes ... with 0 failed recipes`, но одновременно выводит точное сообщение об ошибке; объект помечается удалённым, а следующий чистый reload возвращает штатные `8/0`. Автоматический harness проверяет обе части поведения. В логе также остаются две предупреждающие строки о штатных рецептах Create/TFMG, которые KubeJS отдаёт vanilla codec; они не относятся к fixture-рецептам.

Экспорт показывает итоговые ключи после наследования, их роли, типы, значения по умолчанию и функции отдельных ключей. Он не перечисляет schema-level `.heated()`/`.superheated()` и Java-методы фабрики вроде `.processingTime()`, `.machines()` или `.pressure()`; эти методы подтверждены runtime-fixtures.

Перед выпуском релиза всё ещё необходимо:

1. Запустить клиент на обоих профилях и убедиться, что он доходит до главного меню без ошибок загрузки модов.
2. Проверить видимость всех fixture-рецептов в JEI.
3. Фактически выполнить восемь типов рецептов в соответствующих машинах TFMG; VAT pressure отдельно проверить на `current`.
4. После публикации ветки дождаться зелёной GitHub Actions-матрицы и только затем расширять заявленный диапазон версий или выпускать JAR.

Локальные compile/JAR/server-load проверки подтверждают совместимость Java API и принятие fixture JSON кодеками. Полный release qualification остаётся незавершённым, пока не выполнены клиентская и машинная проверки; draft PR допустим, если это ограничение явно указано в его тексте.

## Как поддерживать этот файл

При обновлении зависимости записать новую версию, ссылку на релиз/коммит, профиль и результат четырёх уровней проверки: compile, JAR metadata, server reload, in-machine test. Отдельно различать подтверждённую compile/server-load совместимость и полный допуск релиза. Комбинацию без compile/server-load проверки не включать в диапазон обязательных зависимостей; комбинацию без in-machine проверки явно помечать как не прошедшую полный допуск.
